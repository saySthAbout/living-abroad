# Living Abroad — 통합 테스트(Integration Test) 문서

- 작성일: 2026-07-27
- 대상 브랜치: `main`
- 범위: **실제 DB(또는 실제 Spring 컨텍스트/실제 HTTP 라우팅)**를 통해 여러 계층이 함께 동작하는지 검증하는 자동화 테스트. Mock으로 격리된 순수 로직 검증은 [단위 테스트 문서](Living_Abroad_단위테스트_문서.md) 참고.
- 테스트 환경: 네이티브 PostgreSQL 16 + 직접 빌드한 pgvector 0.8.0(:5432) — 이 개발 머신은 Docker Desktop이 손상된 `dockerInference` 소켓 파일로 기동 불가능한 상태라 native DB로 대체(배포는 `pgvector/pgvector:0.8.2-pg18` Docker 이미지 사용, 완전히 동일한 버전은 아님).
- 실행 명령: `cd backend && ./gradlew test` / `cd ai-server && .venv/Scripts/python.exe -m pytest -q` (단위 테스트와 같은 명령으로 함께 실행되며, 아래 항목만 실제 DB/전체 컨텍스트 사용)

## 왜 이 테스트들이 필요한가

서비스 계층 하나만 Mock으로 격리해서는 드러나지 않는 문제(Flyway 마이그레이션 오류, JPA 매핑 불일치, Spring Bean 배선 충돌, DB 타입 추론 오류, 비동기 트랜잭션 커밋 시점 문제 등)를 잡기 위함이다. 실제로 이 프로젝트에서 이 클래스의 버그가 반복적으로 발생했다 — 채팅 이력 검색의 bytea 타입 추론 오류(PR #29), 분석 상태가 PENDING에 멈추는 비동기 자기호출 버그(PR #26), Google 로그인 추가 시 `JwtDecoder` 빈 2개 충돌 가능성 등. 이런 클래스의 버그는 Mock 기반 단위 테스트로는 잡을 수 없다.

## Frontend

프론트엔드는 Vitest 환경에서 axios/API를 항상 mock 처리하므로(jsdom 환경, 실제 브라우저·실제 백엔드 없음), **실제 통합 테스트에 해당하는 자동화 테스트가 없다.** 프론트-백엔드-AI서버-DB를 전부 연결한 검증은 실제 브라우저로 수동 확인하며, 이는 [시스템 테스트 문서](Living_Abroad_시스템테스트_문서.md)에서 다룬다.

## 한계

- 백엔드 ↔ AI서버 간 **실제 HTTP 호출 경로**(`AiServerClient`가 FastAPI를 호출하는 부분)는 자동화된 통합 테스트가 없음 — AI 서버가 죽었을 때 503으로 처리되는지는 예외 핸들러 단위 테스트로만 커버되고, 두 서버를 함께 띄운 연결 검증은 [시스템 테스트 문서](Living_Abroad_시스템테스트_문서.md)의 수동 확인(ST-16)에 의존한다.
- pgvector 통합 테스트(INT_004)는 로컬 네이티브 Postgres(0.8.0)에서만 실행되고, 배포 환경의 정확한 버전(0.8.2)으로는 자동 검증되지 않는다.
